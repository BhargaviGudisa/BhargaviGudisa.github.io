GCP Ingestion Pipeline

Lumin Innovations

Python + Bash ingestion application packaged in Docker, GCP storage and compute provisioned with Terraform. Every Linux environment runs the same version-controlled build — no drift between dev and production.

PythonBash DockerTerraformGCP
Internal — source not public
Problem

The same ingestion code behaved differently depending on which Linux box it ran on. Environments were built by hand, so dev and production drifted apart and failures surfaced in one place but not the other — the slowest kind of bug to chase, because reproducing it is the hard part.

Approach
  • Packaged the Python and Bash application into a Docker image so the runtime, interpreter version and system dependencies are fixed at build time rather than inherited from the host.
  • Declared the GCP storage bucket, compute instance and service account in Terraform, so infrastructure changes go through review as code instead of being clicked into a console.
  • Kept one plan across environments — the difference between dev and production is a variables file, not a different procedure.
Architecture
Terraform owns the compute and storage layer; the image owns everything above it

AI Quality Evaluation Framework

Lumin Innovations

Python + Bash tools analyzing 5,000+ AI-generated responses, flagging quality gaps at 98% accuracy. Root-cause separation between content gaps and prompt-handling failures cut engineering debugging time by 30%.

PythonBash QA AutomationRoot-cause Analysis
Internal — source not public
Problem

Thousands of AI chat responses needed review, and a wrong answer had two possible causes: the knowledge base genuinely lacked the fact, or the fact was there and the model failed to use it. Nobody knew which without investigating, so every failure was checked twice — once by content owners, once by engineers — and one of those investigations was always wasted.

Approach
  • Built Python and Bash tooling to analyse responses at volume and produce remediation reports engineers could prioritise from, rather than a raw list of complaints.
  • Designed a root-cause separation rule applied before the ticket reaches a human: if retrieval found nothing, it is a content gap; if retrieval found the entry and the answer did not cite it, it is a prompt-handling bug.
  • Routed each class to the one team that can fix it, so a failure arrives with an owner already attached.
The deciding logic
classify_failure.py
def classify_failure(response, kb_hit, prompt_trace):
    # One failure, one owner. The split below is the whole point:
    # before it, engineers checked both causes on every bad answer.

    if not kb_hit.found:
        # the knowledge base genuinely lacks the fact
        return Failure("content_gap", owner="kb_owner", area=kb_hit.area)

    if not prompt_trace.cited(kb_hit.entry_id):
        # it was retrievable and still missed — model side, not content
        return Failure("prompt_handling", owner="engineering",
                       trace=prompt_trace.id)

    return None   # grounded and cited — not a failure

Content Governance Automation

Lumin Innovations

Governance framework with per-area ownership and automated Bash audits routing 200+ stale knowledge-base entries monthly to owners — cutting content staleness by 45% and replacing a fully manual process.

BashJira GovernanceAutomation
Internal — source not public
Problem

No one owned any particular area of the knowledge base. Reviews happened when someone noticed a problem, which meant content decayed quietly and the people best placed to fix an entry were never told it had gone stale. Auditing it by hand did not scale, and it was the first thing dropped under deadline pressure.

Approach
  • Assigned one owner per content area so every entry has a name attached before it ever goes stale.
  • Made review a release-gated step tracked in Jira, rather than an intention.
  • Automated detection in Bash and had the audit open the review ticket against the mapped owner — the script does the routing, not a person.
  • Made an unmapped area a hard failure: better to break the run than to silently skip entries nobody owns.
The audit
audit_kb.sh
#!/usr/bin/env bash
# Route stale knowledge-base entries to the owner of their area.
set -euo pipefail

STALE_AFTER_DAYS=180
OWNERS="config/area-owners.tsv"

while IFS=$'\t' read -r entry area last_review; do
  age=$(( ( $(date +%s) - $(date -d "$last_review" +%s) ) / 86400 ))
  [[ "$age" -lt "$STALE_AFTER_DAYS" ]] && continue

  owner=$(awk -F'\t' -v a="$area" '$1==a{print $2}' "$OWNERS")
  # fail loud: an unmapped area must never be silently skipped
  : "${owner:?no owner mapped for area $area}"

  jira_create_review "$entry" "$owner" "$age"
done < <(kb_export --fields id,area,last_review)

Coffee Sensory Quality Data Pipeline

Personal · Public Dataset

Python pipeline cleaning 1,300+ Arabica cupping reviews from the Coffee Quality Institute, applying quality rules, loading to Azure SQL. Every rejected record is logged with its failing rule — no silent drops. Data lineage published to GitHub.

PythonPandas Azure SQLPower BIGitHub
Repository being prepared for publication
Problem

The Coffee Quality Institute dataset is public and messy — missing scores, unparseable harvest years, absent countries of origin. The normal way to handle that is to drop bad rows during the load, which leaves a clean table and no idea what is missing from it or why. An analyst downstream cannot tell the difference between “no data” and “data we quietly threw away”.

Approach
  • Wrote the quality rules as named, individually testable predicates rather than conditions buried in a load script.
  • Sent every rejected row to a reject table tagged with the rule that rejected it, so exclusions are queryable instead of invisible.
  • Loaded clean records to Azure SQL and surfaced them in Power BI, with every loaded score traceable back to its source row.
  • Published the lineage and a data dictionary to GitHub so other analysts can reuse the model instead of re-deriving it.
Architecture
Rejects are a branch of the pipeline, not a side effect of it
The rules
validate.py
REJECT_RULES = {
    "missing_cup_points": lambda r: pd.isna(r.total_cup_points),
    "score_out_of_range": lambda r: not 0 <= r.total_cup_points <= 100,
    "missing_country":    lambda r: pd.isna(r.country_of_origin),
    "bad_harvest_year":   lambda r: parse_year(r.harvest_year) is None,
}

def validate(df):
    clean, rejected = [], []
    for row in df.itertuples():
        failed = [name for name, rule in REJECT_RULES.items() if rule(row)]
        if failed:
            # keep the row AND the reason — a drop you cannot query
            # is indistinguishable from data that never existed
            rejected.append({**row._asdict(), "failed_rules": ";".join(failed)})
        else:
            clean.append(row)
    return pd.DataFrame(clean), pd.DataFrame(rejected)
Outcome

Every loaded score traces back to its source row, and every excluded row names the rule that excluded it. The lineage and data dictionary are published, so the model is reusable rather than one-off.

Permit Request Tracker

Portfolio Project

C# ASP.NET Core MVC web app for logging, assigning, and closing permit requests. Normalized SQL Server schema with T-SQL migration for legacy CSV data, before/after execution plans for index design, deployed to Azure App Service.

C#ASP.NET Core SQL ServerEntity FrameworkAzure
Repository being prepared for publication
Problem

Permit requests lived in flat CSV exports. Status was free text, so the same state was spelled three ways; assignment was a name typed into a cell; and there was no referential integrity, no audit trail, and no safe way for two people to work at once.

Approach
  • Designed a normalized schema with permit type and assignee as real lookups rather than repeated strings, modelled through Entity Framework Core.
  • Wrote a T-SQL conversion script that migrates the legacy CSV, coercing dates safely and refusing rows that cannot be parsed instead of inserting nulls.
  • Chose indexes from before-and-after execution plans rather than guessing — the covering index follows what the queue screen actually queries.
  • Validated on both client and server, and deployed to Azure App Service.
Migration & index design
migrate_legacy.sql
-- Legacy CSV -> normalized schema
INSERT INTO PermitRequest (RequestRef, PermitTypeId, Status, SubmittedUtc, AssignedToId)
SELECT    s.request_ref,
          pt.PermitTypeId,                   -- lookup, not free text
          COALESCE(NULLIF(LTRIM(RTRIM(s.status)), ''), 'Open'),
          TRY_CONVERT(datetime2, s.submitted_at, 126),
          u.UserId
FROM      staging.LegacyPermitCsv AS s
JOIN      PermitType              AS pt ON pt.Code  = s.permit_type_code
LEFT JOIN AppUser                 AS u  ON u.Email = s.assigned_email
-- refuse unparseable dates rather than silently inserting NULL
WHERE     TRY_CONVERT(datetime2, s.submitted_at, 126) IS NOT NULL;

-- The queue screen filters on status + date, then joins the assignee.
-- The plan showed that join driving the cost, so cover all three.
CREATE NONCLUSTERED INDEX IX_PermitRequest_Status_Submitted
    ON PermitRequest (Status, SubmittedUtc DESC)
    INCLUDE (RequestRef, AssignedToId);
Outcome

Staff log, assign and close requests against a schema that enforces its own integrity, with legacy records migrated rather than abandoned. Index choices are backed by execution plans captured before and after, so the tuning is evidence rather than intuition.

Review Sentiment & Competitor Radar

Personal · Live demo

Aspect-based sentiment analysis over the Yelp Open Dataset, scoring one business against five nearby competitors across six service aspects. Streamlit dashboard with radar comparison, gap analysis and a filterable review browser.

PythonStreamlit Plotlypandas SQLiteVADER
Source ↗ Live demo ↗
Problem

A small business collects hundreds of reviews and reads almost none of them. The star rating tells an owner they are a 4.1; it does not tell them what to fix first, or where a competitor two streets away is beating them. Aggregate sentiment has the same flaw — one number cannot distinguish slow service from mediocre food.

Approach
  • Scored sentiment per aspect rather than per review — coffee, food, service, wait time, price, ambience — by tagging each sentence to an aspect and scoring it independently.
  • Scoped the comparison deliberately: 6 Philadelphia coffee shops drawn from the dataset’s 6.99M reviews, picked by review volume and proximity, so the competitor set is a real local market rather than an average.
  • Chose VADER and keyword matching over an LLM. The tradeoff is accuracy for cost, speed and explainability — every score traces to the sentences that produced it, and the demo costs nothing to run.
  • Landed the parsed reviews in SQLite between load and analysis, so scoring re-runs without re-parsing the source JSON.
Pipeline
aspect scoring
# Yelp JSON -> load_yelp.py -> SQLite -> analyze.py -> app.py

ASPECTS = {
    "service":   {"staff", "barista", "friendly", "rude"},
    "wait_time": {"wait", "slow", "queue", "line"},
    # ... coffee, food, price, ambience
}

def score_review(text):
    # sentence level, not review level: one review can praise the
    # coffee and damn the wait, and both facts need to survive
    scores = defaultdict(list)
    for sent in sent_tokenize(text):
        hits = [a for a, words in ASPECTS.items()
                  if words & set(sent.lower().split())]
        if not hits:
            continue  # unattributable sentiment is dropped, not spread
        compound = vader.polarity_scores(sent)["compound"]
        for aspect in hits:
            scores[aspect].append(compound)
    return {a: mean(v) for a, v in scores.items()}

The dashboard turns a wall of reviews into one answer: the target business trails its competitors most on food (−0.15), then service (−0.09) and wait time (−0.07) — a ranked list of what to fix rather than a rating to feel bad about. The known limits are stated in the repository rather than hidden: keyword matching misses phrasing an LLM would catch, and the public dataset covers 11 metro areas, so the live demo runs on Philadelphia.

Telco Customer Churn Analysis

Personal · Public Dataset

7,000+ telecom customer records cleaned and segmented to answer the three questions a retention team actually asks: how much recurring revenue is at risk, which segments leave, and which interventions would pay for themselves.

Pythonpandas SQLJupyter
Source ↗
Problem

A churn rate is a number, not a decision. Knowing that 26% of customers leave tells a retention team nothing about who to call first, and acquiring a replacement customer costs far more than keeping the one you have. The question worth answering is not how much churn there is but which segments it concentrates in.

Approach
  • Cleaned and validated the raw dataset first — 7,043 rows down to 7,032 after resolving blank charge fields that would otherwise have been silently coerced to zero.
  • Segmented churn by contract type, tenure, service mix and support level rather than reporting one aggregate, because the aggregate hides the only actionable finding.
  • Quantified revenue at risk per segment, so the recommendations are ranked by money rather than by churn percentage.
  • Specified a dashboard layout for ongoing monitoring, so the analysis does not expire the moment the notebook is closed.
Outcome

Churn concentrates sharply in month-to-month contracts and short-tenure customers, which turns a vague retention budget into a specific target list. The repository carries the cleaning steps, the SQL and Python analysis, and the dashboard specification, so the method is reusable rather than a one-off notebook.

Sales & Revenue Performance

Personal · Retail Dataset

Multi-year retail transaction data cleaned, modelled and analysed into KPIs, profitability drivers and regional performance — the full path from raw transactional rows to a dashboard a manager would actually open.

Pythonpandas SQLPower BI
Source ↗
Problem

Retail organisations generate transactional data continuously and convert very little of it into decisions. The data arrives at the grain of a line item; the questions arrive at the grain of a quarter, a region or a product line. Closing that gap is modelling work, not reporting work.

Approach
  • Loaded and cleaned the raw transaction data, then modelled it before analysing it — dimensions for product, region and time rather than repeated strings on every row.
  • Wrote the analysis in both SQL and pandas, so the same figures are reproducible from the warehouse or the notebook and disagreements surface immediately.
  • Tracked profitability alongside revenue, because the top-selling product and the most profitable product are frequently not the same one.
  • Presented the result as KPIs and dashboard visuals rather than a notebook, since the audience is a manager rather than an analyst.
Outcome

Month-over-month revenue movement, regional performance and the top product and customer cohorts are visible in one view, with the modelling and the queries published so the numbers can be checked rather than taken on trust.
